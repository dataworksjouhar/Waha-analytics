# Al Waha Analytics Platform

A hand-built analytics pipeline and warehouse for a fictional Kuwaiti lifestyle
destination, built as a portfolio piece and a reusable template for real SME
clients.

Built by [Mohammed Jouhar](https://github.com/dataworksjouhar), a Senior
Business Data Analyst (12+ years in retail analytics: Alshaya, Lowe's, Tesco,
Decathlon), with Claude Code as a pairing partner across every session. The
full session-by-session build log is in the git history and
[docs/phase1-runbook.md](docs/phase1-runbook.md).

## What this is

**Al Waha Destination Co.** operates **Al Waha Park**: 10 leased tenants
paying turnover rent, four own-operated venues (a family Playground, a Farm,
Pulse Gym, and an Equestrian Centre with lessons and horse boarding), a
booking website, and D365-shaped ERP exports. Every file is synthetic,
generated by this repo's own generator, and deliberately imperfect in the
ways a real client's data always is: a dead footfall sensor, inconsistent
gate names across files, late and restated tenant sales submissions, null
contract end dates, duplicate member identities across two membership
systems, overbooked lesson slots.

The business is fictional throughout, inspired by (never branded as) real
Kuwaiti operators - Murouj and Sahara Equestrian Resort are named openly as
inspiration, never as the product.

Two goals shape every decision in this repo:

1. **Portfolio and interview credibility.** The design has to survive
   technical questioning: multiple fact grains, a genuine SCD Type 2
   dimension, real data quality problems, honestly handled.
2. **Template reusability.** All client-specific values live in
   `config/client_waha.yml`. A future real client (a perfume retailer, any
   SME with sales + web + footfall data) is meant to be a config change,
   not a rewrite - the schema core (date, product, customer, location) is
   conformed and shared.

Full design rationale: [docs/phase0-architecture.md](docs/phase0-architecture.md).

## Architecture

Medallion layers, all in one Postgres database (Supabase free tier):

- **Bronze** (`data/bronze/`, gitignored): raw generated files, exactly as a
  real vendor/tenant/ERP export would land. Registered in
  `bronze.file_registry` with a checksum, never edited.
- **Silver** (`silver.*`): cleaned, typed, deduplicated, conformed to one
  row per business entity. Every table carries `_source_file`, `_loaded_at`,
  `_dq_flags` - nothing questionable is dropped, only flagged.
- **Gold** (`gold.*`): a star schema - 11 dimensions, 7 fact tables,
  deliberately varied in type (transaction, periodic snapshot, aggregate,
  capacity/coverage) and in grain, because that variety is what a real
  business actually has and what a technical interview actually probes.
  `dim_tenant` is SCD Type 2. `fact_membership_months` reconstructs
  contract-month history from a single latest-snapshot source, because gym
  memberships, equestrian club memberships, and horse boarding are the same
  member-month recurring-revenue shape wearing three different names.
- **DQ** (`dq.check_results`): an append-only audit trail. Every pipeline
  run writes one row per check - row counts, key uniqueness, referential
  integrity, value ranges, freshness - pass or fail, so "data quality is
  the point" is demonstrable, not just claimed.

No Spark, no dbt, no Airflow, no live D365 connection. Transforms are
hand-written pandas on purpose - the point of this project is showing the
thinking, not adopting a framework.

## Stack

Python 3.12+, pandas, Postgres (Supabase), SQLAlchemy, psycopg2. Hand-built
DQ checks module. `pipeline/run.py` as the orchestrator; GitHub Actions cron
is a later phase, not this one.

## Repository layout

```
config/      client YAML (the one place client-specific values live) + schema DDL
generator/   synthetic data generation - two years of messy bronze files
pipeline/
  extract/   schema deploy + bronze file registration/load
  transform/ silver: clean, type, dedupe, conform, flag
  load/      gold: dimension and fact builds, surrogate key lookups
  dq/        the checks module and its dq.check_results writer
  run.py     the orchestrator: schema -> bronze -> silver -> DQ gate -> gold -> DQ gate
sql/         gold reporting views (Phase 2)
app/         Phase 2 frontend, empty for now
tests/       pytest on the transform logic that's easy to get subtly wrong
docs/        architecture doc + the session-by-session runbook
```

## Running it

```bash
python generator/generate.py   # builds two years of messy bronze files (data/bronze/, gitignored)
python pipeline/run.py         # schema -> bronze -> silver -> DQ gate -> gold -> DQ gate
pytest                         # transform logic: SCD2 point-in-time join, churn
                                # reconstruction, mixed tenant date formats, seasonality
```

Both pipeline commands are idempotent: bronze dedupes on file checksum,
every silver/gold table is truncated and rebuilt from the layer below it
each run, so re-running never duplicates a row. `pipeline/run.py` exits
non-zero if a gold-layer DQ check flags real corruption (an error-severity
failure - key uniqueness or referential integrity); row-count, value-range
and freshness checks can legitimately vary a little and only ever warn.

## The 12 business questions gold has to answer

The GM of a destination like this genuinely cannot answer these from raw
exports today. This is the list Phase 1's gold layer was built against
(full detail in the architecture doc, section 9):

1. Daily footfall vs last week/last year, with a weather overlay
2. Footfall-to-sales conversion for the own-operated venues
3. Turnover rent owed vs collected, and who's late
4. Sales per square metre by tenant category
5. Online vs walk-in ticket mix
6. Website conversion rate by channel
7. Event ROI: uplift vs baseline footfall and sales
8. Membership active base and churn (gym + equestrian club)
9. Revenue mix: own venues vs rental income vs recurring memberships
10. Average transaction value by venue
11. Riding lesson slot utilization and no-show rate, by level and instructor
12. Stable occupancy and boarding revenue, the recurring-revenue base
